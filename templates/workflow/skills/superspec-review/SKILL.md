# SuperSpec Review

你负责完成代码审查、最终验证和交付确认。这个阶段用来提高实现质量，不用来增加额外审批负担。

## 使用方式

先运行 `superspec transition next --change "<change>"`。把输出当作当前任务卡：它会告诉你是需要审查、验证、用户决策、修复，还是可以完成交付；不要自行解释内部流程、风险参数或旧工作项来决定下一跳。

- 返回审查/验证工作项：按「工作项处理」完成并登记报告。
- 返回用户确认：按输出取得所需确认并登记；涉及业务范围、需求或验收取舍时，必须由使用者决定，不能用技术判断代替。
- 返回修复动作：只按当前输出给出的修复方向处理；修复后重新获取下一步。
- 返回交付动作：确认没有待处理事项后再执行。

代码变化会使先前的审查结论失效；计划材料或执行证据变化会使验证结论失效。不要试图手动复用旧结论，重新运行 `next` 即可得到需要补做的事项。

## 工作项处理

如果 next 返回代码审查或最终验证工作项：

1. 读取工作项说明（job packet）。
2. 启动对应独立角色执行只读审查或验证。
3. 按工作项说明中的提交命令提交 JSON 报告，优先从 stdin 提交。

```bash
superspec record job-submit --change "<change>" --job <JOB> --report -
```

文件路径模式仅作为备用。报告登记沿用现有事件和原始报告归档机制；不要新增追溯字段或自定义原始报告文件类型。

代码审查结果处理：

- 报告必须给出可验证、可处理的结论；格式或内容不合格时，按返回原因修正审查方式后重新提交。
- 发现纯代码实现问题：按当前输出给出的修复动作处理。
- 发现方案/需求文档问题或混合问题：让使用者决定处理方向并登记原因；不要擅自选实现或计划路径。

最终验证结果处理：

- 最终验证通过后，只有 `next` 明确给出交付动作时才执行。
- 最终验证未通过：按报告中的问题修复或回退；不要直接交付。

## 交付后有新需求

- 使用者补充、修正或扩展方案、需求、验收或实现约束时，主流程只需确定对应的 change；引擎会给出重新计划的动作。不要让使用者选择内部工作流动作或执行命令。
- 问答、致谢或不改变方案含义的说明不触发返工。
- 新需求必须先回计划材料澄清，不直接作为编码授权。

## Guardrails

- 审查阶段只读，不改业务代码。
- 不绕过 `next` 要求的代码审查或最终验证。
- 主流程不重审代码，只复核代码审查报告是否可登记、问题是否可分流、回退和闭环证据是否存在。
- 涉及代码审查问题时，以当前输出为准，不手动套用旧 job 或旧问题编号。
- 审查和验证报告必须引用真实文件、事件或测试证据，不编造。
- 不手写推进或回退结果。
