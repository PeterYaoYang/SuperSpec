# SuperSpec 工作流评测 — 终局架构

| 字段 | 值 |
|---|---|
| 状态 | **已定稿** |
| 日期 | 2026-07-12 |
| 设计来源 | 三步目标 + [Anthropic 评测指南](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents) |
| 范围 | 评测系统本身的设计。被测对象 = SuperSpec 工作流（skills + 引擎），**默认不改产品代码**；评测发现的问题进人工待办清单 |

---

## 0. 这个系统是什么（一句话）

> 一个**可重复的「模拟人把工作流用到需求完成」的考场**：每个需求在隔离环境里由「模拟用户 + 工作者」协作推进某个工作流（默认 SuperSpec）直到完成；完成后两位独立 AI 评审对照「需求 vs 结果」复盘，并用全程记录把问题归因到具体责任方，形成工作流的优化待办清单。
> 它存在的唯一理由：**让工作流每次更新后，不必再靠真人手测也能持续发现问题**。

---

## 1. 痛点（要打破的循环）

```text
工作流每次更新
  → 只能靠真人拿真实需求手测
  → 一两次还行，每次更新又出新坑
  → 人嫌烦 → 不再用工作流
  → 不用 → 发现不了问题
  → 改不好 → 更不敢用
```

**根因不是「跑得慢」，而是「没有可持续、不消耗人耐心的验证方式」。** 本系统的使命就是切断这条循环。

---

## 2. 终局目标（三步）

```text
① 需求         自动生成（可选）│ 人工指定
② 考场         模拟用户 + 工作者，用某工作流（默认 SuperSpec skills）
               逐步推进，直到「需求完成」
③ 复盘 + 归因   两位独立 AI 评审对照「需求 + 最终结果」
               再结合全程记录 → 问题点 + 可优化点 + 责任归因
```

**「完成」由任务自己声明**：任务说它要达到工作流的哪个完成态（SuperSpec 例：`review` / `accepted` / 或中间态 `propose_ready`）。评测**不发明**完成定义，只**判定**是否真到了，且是否由工作者真实驱动（不是作弊刷出来的）。

---

## 3. 设计原则

| 原则 | 含义 |
|---|---|
| **判结果，不判路径** | 看「是否达到完成 + 产物对不对」，不死卡「有没有走某一条固定工具序列」（同一目标可以有多种合法走法） |
| **调度器中立** | 评测程序自己绝不替任何人按确认、绝不替任何人改工作流状态——否则评测就是在测自己，没意义 |
| **无证据不归因** | 任何「这个问题怪谁」的结论，必须引用全程记录里的具体证据，否则降级处理 |
| **任务要清晰** | 一道题必须好到「两个专家独立看能判出同一结论」；模糊题不收 |
| **回归集切断死循环** | 每次工作流更新自动跑一批固定任务，不靠人 |
| **改产品要人确认** | 评测只产待办清单；真要改 SuperSpec 代码/skills，须人审核 |
| **多层判定互补** | 结果判定 / 真实性判定 / 双审 / 归因 / 人工抽检，叠在一起用，单层都不够（像瑞士奶酪叠层，每层有洞，叠起来挡住） |
| **隔离即可复现，不是红队攻防** | 用独立工作副本 + 固定版本；目标是「多次运行结果可统计比较」，不是「防黑客攻击」。AI 模型本来就不可能比特级一模一样重跑 |

---

## 4. 角色

| 角色 | 是谁 | 能做 | 不能做 |
|---|---|---|---|
| **模拟用户** | 扮演提需求的人 | 给需求、答澄清、在工作流弹出的确认点用**真实选项**确认/拒绝、扩/收范围 | 读工作者工作区或记录、主动泄露隐藏信息、机械「继续」绕过确认 |
| **工作者** | 扮演用工作流的开发者 | 自然调用工作流入口（skills/命令行）、领任务/交产物、失败重试 | 让调度器代推状态、读题底 |
| **调度器** | 评测主程序 | 启停会话、轮流发言、转发消息、记全程日志 | **碰工作流状态**、替用户确认、教工作者该走哪步 |
| **评审 A / B** | 两位独立 AI 评审 | 对照需求+结果+日志切片，提问题/优化建议 | 改硬判定、编造没发生的事 |
| **归因器** | 规则+模型 | 把评审意见 + 硬判定 + 全程日志映射到「怪谁」 | 自动改产品 |
| **人** | 研发 | 接待办清单、改工作流、维护回归集 | —— |

## 5. 系统架构

### 5.1 整体流程（端到端）

```text
        ┌──────────────────────────────────────────┐
        │  任务库                                    │
        │  手写 │ 可选生成器 │ 资格门                 │
        └─────────────────┬────────────────────────┘
                          │ 一个任务
                          ▼
        ┌──────────────────────────────────────────┐
        │  考场（隔离工作副本 + 工作流已装 + 固定版本）│
        │   模拟用户 ◄──► 调度器(中立) ◄──► 工作者    │
        │                       │                  │
        │                       ▼  只有工作者能改状态│
        │                工作流引擎 + skills（被测）  │
        └─────────────────┬────────────────────────┘
                          │ 全程日志（带「谁/何时/为何」）
                          ▼
        ┌──────────────────────────────────────────┐
        │  判定（多层互补）                           │
        │   1. 结果判定  2. 真实性判定               │
        │   3. 双审(A+B)  4. 归因                    │
        └─────────────────┬────────────────────────┘
                          │ 报告 + 待办清单
                          ▼
        ┌──────────────────────────────────────────┐
        │  回归集 + 人工审核 → 改工作流 → 再跑        │
        └──────────────────────────────────────────┘
```

### 5.2 模块

| 模块 | 职责 |
|---|---|
| **任务定义** | 需求正文、成功标准、目标完成态、隐藏信息、预算、绑哪个工作流 |
| **任务来源** | 手写库 + 可选生成器 + 资格门（双专家一致） |
| **考场** | 物化隔离工作副本、装工作流、固定版本；保证隔离与多次运行可比较 |
| **调度器** | 轮流发言 + 转发消息 + 记日志；**没有改状态的权力** |
| **全程日志** | 统一记录：每条消息/命令调用/工作流事件/确认/产物变更，都带「谁/何时/为何」 |
| **结果判定** | 确定性：是否到目标完成态 + 关键产物在 + 工作流自身不变量满足 |
| **真实性判定** | 确定性：工作流状态的每次推进，**真能对应到工作者的真实动作**（不是调度器干的、不是伪造的） |
| **双审** | 两位独立 AI 评审：需求符合度、实现质量、流程摩擦、优化建议 |
| **归因器** | 把评审意见 + 硬判定 + 全程日志 → 责任类（题/模拟用户/工作者模型/skill/引擎/环境）+ 去重 |
| **回归集** | 固定绿任务 + 稳定性指标；工作流更新必跑 |

### 5.3 信任边界（承重）

```text
                  改工作流状态   读题底          读对方会话
模拟用户             否         仅经隐藏信息通道    否
工作者               是（唯一）   否               否
调度器               否（永远）   否               否
判定/评审            否         仅脱敏材料         否
```

**唯一不变量：工作流状态只能由工作者经工作流自身入口产生。** 任何调度器/评测侧的状态写入 = 这次运行作废。

### 5.4 怎么保证「状态真是工作者改的」（防伪造）

上表只是「规矩」。但全程日志是评测程序自己写的，理论上它能伪造「这条是工作者干的」。所以要有一个**被测方伪造不了的事实依据**。

SuperSpec 引擎**本来就有**：
- `.superspec/changes/<id>/events.jsonl`：工作流每次推进状态都会往里加一条事件
- `.superspec/changes/<id>/snapshot.json`：当前状态

判定真实性的方法（**不用改 SuperSpec**）：

1. **直改文件会被发现**：工作者若绕过引擎直接改状态文件，`events.jsonl` 里就不会有对应事件 → 判失效。
2. **每次状态推进，必须能对应到调度器亲眼看到的、工作者确实发起的一条命令调用**（调度器从外部观测工作者子进程，记下命令行、退出码、时间）。对不上 → 判失效。
3. **不看引擎里的「actor」字段**：那是环境变量，工作者自己就能改，不可信。

> 一句话：**「状态有变化 ↔ 确实有工作者在那一刻发起过命令」必须一一对应**，否则视为作弊。

这种「引擎单一写入 + 调度器外部观测」的做法，没有多份各自计算的摘要，天然不会漂移。

### 5.5 隐藏信息怎么给模拟用户

模拟用户能看到的「题底」（隐藏信息），**只能由评测程序在题目指定的时机注入**（比如「被问到 X 时才披露 Y」）；模拟用户**不能**自己直接去读题底文件。工作者始终看不到题底。

### 5.6 一次运行产出的文件

```text
runs/<运行id>/
  task.json                 # 任务定义快照
  transcript.jsonl          # 全程带归属记录
  arena/                    # 隔离工作区（工作副本 + 已装工作流）
    workflow-state/         # 被测工作流自己的状态（引擎/skills 产）
    artifacts/              # 产物
  private/                  # 题底；工作者不可见
  sessions/{模拟用户,工作者,评审a,评审b}/
  grading/
    outcome.json            # 结果判定
    liveness.json           # 真实性判定
    review_a.json
    review_b.json
    attribution.json        # 归因
  report.md
```

## 6. 判定模型（四层 + 人工抽检）

### 第 1 层：结果判定（确定性）
- 是否达到任务声明的完成态？
- 关键产物是否存在且非空？
- 工作流自身不变量是否满足（由工作流自己定义，评测只读）？

### 第 2 层：真实性判定（确定性）
- 工作流状态的每次推进，是否都能在日志里找到**对应的工作者真实动作**？
- 有没有「状态自己跳了」（调度器或未知来源写入）？
- 工作者是**真的用了工作流入口**，还是绕过引擎直接改文件伪造完成？

> 真实性不过 → 即使结果看着到完成态，也判**不成立**（防机器化空洞绿：表面上全过了，其实全是作弊刷的）。

### 第 3 层：双审（两位独立 AI 评审）
输入（脱敏材料包）：任务公开部分 + 结果摘要 + 日志关键切片 + 第 1/2 层结构化结果（只读）。
每位独立产出：

```json
{
  "requirement_fit": "需求符合度 0~1",
  "issues": [{ "what": "问题", "severity": "P0|P1|P2", "evidence_ref": "证据指向" }],
  "workflow_optimizations": [{ "target": "skill|gate|engine|packet|docs|task", "suggestion": "建议", "evidence_ref": "证据指向" }],
  "confidence": "把握度 0~1"
}
```

合并：两边意见合并、冲突标记；**没有证据指向的建议必须降权**；评审**不能**改硬判定。

**证据指向**的格式（必须能定位到具体记录）：`engine_event:<id>`（引擎事件）/ `transcript:<序号>`（日志条目）/ `artifact:<路径>`（产物）。定位失败 = 该条降权。

**第 3 步的分工**（用户把「双审 + 全日志归因」捆在第 ③ 步）：**双审管「需求符合度 + 流程摩擦」**（基于切片）；**归因器管「全日志归因 + 责任类」**（基于全日志 + 前面各层）。两者都喂优化待办，不重复、不冲突。

### 第 4 层：归因
消费：第 3 层产出 + 第 1/2 层硬判定 + 全程日志。
输出责任归类 + 去重后的优化待办：

| 责任类 | 含义 |
|---|---|
| `task` | 题目本身有问题 |
| `user-sim` | 模拟用户不真实 |
| `worker-model` | 工作者模型能力不足 |
| `workflow-skill` | skill 文案/流程问题 |
| `workflow-engine` | 引擎/状态机问题 |
| `env` | 隔离/版本/工具链 |

### 人工抽检
定期人工校准双审、接纳待办、维护回归集。

### 合并规则
- 第 1/2 层是**硬**：失败压过一切赞美
- 第 3 层默认**仅供参考**：不自动翻转硬判定
- 缺关键证据 → **`UNKNOWN`（证据不足）**，不发明结论

**最终状态词**（没有含糊的「PASS」）：

| 状态 | 含义 |
|---|---|
| `DONE` | 第 1+2 层都过（真实驱动到目标完成态） |
| `PROVISIONAL_DONE` | 仅第 1 层过，真实性判定还没上（早期阶段用，**不能当人测替代/发布门**） |
| `DONE_BUT_FLAWED` | 第 1+2 层过（真实完成），但双审提了 P1/P2 问题（仅供参考，**不阻断**硬判定） |
| `NOT_DONE` | 没到目标完成态 |
| `NEEDS_HUMAN` | 模拟用户遇到未授权或信息不足的真实业务决策，安全停止并等待真人输入 |
| `INVALID` | 隔离/作弊破坏/防伪造检查没过 |
| `UNKNOWN` | 证据不足，不下结论 |

## 7. 完成态与「全流程」

- 任务**可声明任意完成态**，包括全流程到 `accepted`。
- 但声明越远的完成态，预算/稳定性成本越高；回归集按完成态分级。
- 若工作流自身还没实现某完成态的可达路径，那是**工作流的 bug**，评测如实报 `NOT_DONE` + 归因到 `workflow-engine`。

---

## 8. 模拟用户要像人（核心难点）

模拟用户要**像人**，否则测不到工作流的真实摩擦：

| 设计点 | 选择 | 理由 |
|---|---|---|
| 确认选项从哪来 | **工作流实时弹什么，用户选什么** | 测的就是工作流的确认点设计 |
| 能不能拒绝 | **能拒**（按人设/范围） | 真人会拒；永不拒绝 = 测不到范围控制 |
| 能不能提问 | **能澄清** | 真人会问 |
| 能不能「开天眼」 | **禁** | 不能读了工作区/记录后装全知 |
| 失败态度 | **不无限配合刷绿** | 要暴露摩擦，不是掩盖 |

与「永不拒绝、只管推进」型模拟器**刻意不同**——那是测「装了 skill 能不能交付」，本系统测「工作流本身好不好用」。

## 9. 回归集（切断死循环的关键）

- **绿任务集**：人工挑选的、当前能稳定 `DONE` 的任务
- 每次工作流更新 → 自动跑绿任务集 + 计稳定性（多次运行全过才算稳）
- 绿任务退化 → 阻断发布；新发现的 bug → 修后**加进绿任务集**（防再犯）
- 分级：冒烟（秒级）/ 每夜 / 发布门
- **作弊任务集（和绿任务集同等重要）**：故意注入作弊（调度器改状态、工作者绕引擎改文件、伪造归属、自报假命令调用）→ **必须**被识破为 `INVALID`。作弊任务任何一条没被识破 = 阻断发布。这保证真实性检测器不会随工作流更新悄悄退化（否则就是机器化重现用户的死循环）。

> 这才是「不再靠人手测」的落点：人维护绿任务集 + 作弊任务集 + 待办清单，机器跑回归。

---

## 10. 需求生成（可选，后置）

- 生成器产任务定义 → 资格门过滤（双专家一致能判；含可验证的完成态；无歧义）
- 第一版**不做生成器**，先用人工任务池把主链路打通；留好任务定义的生成接口

## 11. 实现复用说明

实现时复用现有 evals/ 代码作为零件，语义按本架构定义：

| 本设计概念 | 可复用的现有零件 |
|---|---|
| 考场 | 现有的 trial 物化 / wrapper / 双树布局 |
| 全程日志 | 现有的 journal + events |
| 真实性判定 | 按 §6 第 2 层实现（引擎事件 + 调度器外部观测） |
| 双审 | 现有的 Sol/Terra「模型可换」配置思想；评分细则/运行器新写 |

复用还是重写，实现阶段按情况决定。

## 12. 分阶段交付（路线）

| 阶段 | 交付 | 完成标志 |
|---|---|---|
| **R0** 主链路打通（**早期、不可当人测替代**） | 考场 + 模拟用户/工作者 + 调度器 + 全程日志 + 结果判定 | 一个手写任务能跑到 `PROVISIONAL_DONE`（仅结果判定）或 `NOT_DONE`。**明确：R0 没有真实性判定，空洞绿风险未消除，不得作为发布门或人测替代** |
| **R1** 真实性判定 | 防伪造依据（§5.4）+ 真实性校验 + 作弊任务集（§9） | 假绿能被识破；`PROVISIONAL_DONE` 升级为可信 `DONE` |
| **R2** 双审 | 两位 AI 评审跑「需求 vs 结果」 | 稳定产问题 + 优化建议 |
| **R3** 归因 | 责任归类 + 待办清单 | 周级可消费的优化列表 |
| **R4** 回归集 | 绿任务集 + **作弊任务集** + 稳定性 + 发布门 | 工作流更新必跑、退化阻断 |
| **R5** 任务生成（可选） | 生成器 + 资格门 | 生成任务不劣于手写 |

**默认下一刀：R0**（先把「模拟人跑到完成」主链路在隔离里打通，输出 `PROVISIONAL_DONE`/`NOT_DONE`；紧接着 R1 上真实性判定才能消除空洞绿）。

## 13. 风险与缓解

| 风险 | 缓解 |
|---|---|
| 模拟用户不像人 → 测不到摩擦 | §8 能拒/能问/不开天眼；人设显式 |
| 调度器作弊刷绿 | 调度器中立 + 防伪造依据（§5.4）+ 作弊任务集（§9，和绿任务集同等阻断） |
| 机器化空洞绿（结果到了但是假的） | 第 2 层真实性判定强制 |
| 评审说空话 | 强制证据指向；无证据降权 |
| 任务质量差、全怪题目 | 资格门 + 双专家一致标准 |
| 成本爆炸 | 绿任务集分级 + 多 run 抽样 + 按完成态预算 |
| 误以为「终局已实现」 | 状态词汇明确；路线与实现分开标注 |
